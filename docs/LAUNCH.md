# EarnAhead launch handoff

Code is prepared for an Atlanta beta. This is not a certification of production readiness. Complete the configuration and real-environment checks below before public signup.

## Remaining owner actions, in order

1. **Framework upgrade completed.** Next.js 15.5.27 is installed with your approval. The current dependency audit reports zero vulnerabilities, and the production security CI gate remains enabled.
2. **Apply the launch migration once.** In PowerShell in this project run `Get-Content .\supabase\migrations\003_launch.sql -Raw | Set-Clipboard`. Switch directly to Supabase SQL Editor, paste the clipboard contents and Run. This adds reporting, deletion, freshness metadata and background-job state. It does not import listings. This launch migration can safely be rerun; do not rerun the original setup script.
3. **Run real database security tests.** Copy `supabase/tests/security.sql` into the SQL Editor and Run after the migration. It tests private data across two accounts and rolls back fixtures. Unit tests do not substitute for this. Save the successful result; investigate any failure before launch.
4. **Choose hosting and a domain.** Deploy the repository to your hosting account. Set the existing `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY`. Set `NEXT_PUBLIC_SUPPORT_EMAIL` to a monitored real address, rebuild, then review the published privacy and terms pages with the actual operator details and hosting/retention practices. Current policy copy describes implemented functionality; it still needs your approval and business-specific details.
5. **Configure auth.** Set Supabase Site URL to your HTTPS domain. Allow the production `/auth/callback` URL and `/auth/callback?next=/reset-password` URL. Remove unnecessary localhost/preview redirects from the production project. Configure custom SMTP, sender domain authentication, email limits, CAPTCHA/abuse controls as appropriate, and MFA for reviewer accounts. If Google login is offered, configure its OAuth credentials and callback. Test real signup and password-recovery emails after deployment.
6. **Enable unattended jobs.** Add server-only `SUPABASE_SERVICE_ROLE_KEY` and a random `CRON_SECRET` of at least 32 characters to hosting secrets. Never put them in public variables or commit them. `vercel.json` schedules `/api/cron/sync` daily at 07:00 UTC; Vercel injects the configured Bearer cron secret. Each run imports one registry page and refreshes 20 existing facility records, saving cursors. For faster coverage configure a more frequent schedule on a plan supporting it. The default schedule is incremental, not a daily full-directory refresh. Donation compensation is not scraped automatically; reviewers recheck source pages. Confirm the admin background-job status records a successful run. Configure host alerts for cron HTTP failures and errors.
7. **Configure operations.** Use `/api/health` for an external uptime check with failure notifications to you. Enable hosting error-log alerts. Choose and enable a database backup/PITR plan, then restore a backup into a separate test project and verify records and authentication. No backup restoration has been performed by Codex. Restrict dashboard membership and keep server keys out of browser code.
8. **Complete real-browser acceptance.** On mobile and desktop test signup/confirmation, recovery link/new password, sign-in/session refresh/sign-out, profile autosave, location denied/manual ZIP search, empty results, known/unpublished pay labels, saved items, underage application refusal, earnings, listing reports, report resolution and account deletion using disposable accounts. Verify account A cannot read or modify B's records and a participant cannot access admin imports/cron. Test slow network, keyboard focus, zoom and screen-reader labels. Browser verification was unavailable during implementation; do not claim it has been performed.
9. **Data launch review.** Use a small Atlanta cohort. Recheck provider sources, dates, payment periods and transit destinations. Approve only reviewed records. Recruiting studies with no published amount must say compensation unknown, not imply payment. Reopened/changed registry listings require manual review; jobs never automatically approve.

## Monitoring and incident response

- The reviewer page shows background-job status, unresolved reports and sources needing freshness review. `sync_state` stores the last successful completion and cursor; a failed run retains the cursor and returns HTTP 500 for host alerts.
- If a source/provider report indicates a closed or incorrect listing, hide it for review before changing the terms. Do not collect health details through reports or support.
- On an outage: inspect the health endpoint and hosting/Supabase status, pause imports if needed, restore from a tested backup into an isolated project, verify migrations/RLS, and only then switch traffic.
- No external alert vendor, email provider, backup subscription or hosting deployment has been configured automatically. These require account access and owner choices.

## Maps and geocoding
City-name search uses the bundled 2025 US Census Places Gazetteer without an API key. A commercial `OPEN_METEO_API_KEY` is optional for additional place matches. Map titles are inserted as text, not HTML. OSM tiles use the official URL with visible attribution and browser referrers, with no prefetching. Choose a production tile provider if you need guaranteed capacity; `NEXT_PUBLIC_MAP_TILE_URL` lets you switch providers. Verify provider attribution requirements before using an alternate tile service. References: [Open-Meteo geocoding](https://open-meteo.com/en/docs/geocoding-api), [OSM tile policy](https://operations.osmfoundation.org/policies/tiles/).
